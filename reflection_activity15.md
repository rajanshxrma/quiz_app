1) I started with the question data model before touching anything else because the whole app depends on it. the api returns json with incorrect_answers as a separate list from correct_answer, so the first thing I had to do was combine them into one list and shuffle it. if I built the ui first without that, the correct answer would always show up in the same position every time which would make the quiz pointless. I also added basic html entity decoding right in the model because I knew from looking at the api response that opentdb sends back encoded characters like &quot; and &#039; in the question text. better to decode it once in the model than scatter that logic around the ui.

2) the api service is pretty simple but the key thing is separating it from the widget entirely. I made it a static method on its own class so the quiz screen doesn't have to know anything about http or json parsing — it just calls ApiService.fetchQuestions() and gets back a list of Question objects. I wrapped the whole thing in a try-catch so if the network request fails or the json is malformed, it throws a meaningful exception instead of just crashing with a null pointer. I tested it worked by checking the console output before wiring up the ui, which is the approach the activity guide recommended.

3) the trickiest part of the state management was the _answered boolean flag. I use it to disable all the answer buttons after the user picks one, and to control the color feedback — green for correct, red for wrong, grey for the other unchosen options. the issue I ran into was that ElevatedButton has both backgroundColor and disabledBackgroundColor as separate style properties, and if you only set one, the disabled state ignores your color and falls back to the theme default grey. I had to explicitly set disabledBackgroundColor to the same color as backgroundColor for the feedback colors to actually show up after the button was disabled.

4) I handled the loading and error states separately before rendering any quiz ui. if _loading is true the screen just shows a centered spinner. if the questions list comes back empty (which would happen if the api call failed and the catch block ran), it shows an error message with a retry button instead of crashing trying to render an empty list. the final score screen is also handled inline by checking if the user just answered the last question — rather than navigating to a new route, I just render a completely different widget tree from the same build method, which keeps the state management simple and avoids any weird navigation stack issues.

5) if I had more time the main thing I'd add is category and difficulty selection on a home screen so the user can customize the quiz before starting. right now it's hardcoded to easy general knowledge which is fine for a demo but gets boring fast. I'd also add a timer per question to make it more of a real quiz experience. and I'd look into persisting the high score with shared_preferences so it survives app restarts, similar to how I'd improve the message log in the fcm app.
